# Блок 3. Контролируемое применение исправлений

## Цель

Добавить безопасный исполнитель для предложений, которые пользователь вручную подтвердил в листе `11 Предпросмотр`.

Контур остаётся отключённым после установки и не меняет `01 Операции`, пока одновременно не выполнены два условия:

- в `09 Настройки` параметр `quality_apply_enabled` равен `TRUE`;
- `PR_CONFIG.ALLOW_OPERATION_WRITES` равен `true`.

## Разрешённые изменения

Автоматически применяются только предложения типов:

- `MISSING_CATEGORY`;
- `MISSING_DESCRIPTION`.

Фактическое поле дополнительно проверяется по белому списку заголовков: `Категория`, `Описание`, `Комментарий`, `Назначение`.

Не применяются автоматически:

- исправления дат;
- исправления сумм;
- удаление или объединение дублей;
- любые предложения с пустым новым значением;
- предложения без статуса `ПОДТВЕРЖДЕНО`.

## Защитные механизмы

1. Fail-closed по двум независимым переключателям.
2. Лимит одного запуска — 10 строк.
3. Document Lock исключает параллельное применение.
4. Перед записью повторно проверяются:
   - номер строки;
   - ID операции, если столбец ID существует;
   - текущее значение ячейки;
   - разрешённость типа проблемы и целевого поля.
5. После записи значение перечитывается. При несовпадении исходное значение восстанавливается.
6. Для каждого успешного изменения создаётся запись в `12 Резерв исправлений`.
7. Очередь получает статус `ПРИМЕНЕНО` или `ОШИБКА ПРИМЕНЕНИЯ` и диагностический комментарий.
8. Выполняется аудит каждой строки и всего пакета.

## Установка на DEV-книге

1. Опубликовать файлы `QualityApplyService.js` и `QualityApplyBootstrap.js` в связанном Apps Script проекте.
2. Запустить `prhInstallQualityApply` из редактора Apps Script.
3. Обновить таблицу и открыть меню `Качество: применение`.
4. Выполнить `Проверить готовность`.

Установщик намеренно создаёт параметр `quality_apply_enabled=FALSE`.

## Безопасный сценарий проверки

1. Оставить `PR_CONFIG.ALLOW_OPERATION_WRITES=false` и убедиться, что проверка показывает блокировку.
2. Подтвердить в очереди не более одной тестовой строки `MISSING_CATEGORY` с непустым предложенным значением.
3. Создать резервную копию DEV-книги.
4. Временно установить оба разрешения в активное состояние.
5. Повторно выполнить `Проверить готовность`.
6. Выполнить `Применить подтверждённые`.
7. Проверить:
   - изменена ровно одна разрешённая ячейка;
   - создана строка в `12 Резерв исправлений`;
   - предложение получило статус `ПРИМЕНЕНО`;
   - в аудите есть события `QUALITY_APPLY_ITEM` и `QUALITY_APPLY_BATCH`.
8. Сразу выполнить `Отключить применение` и вернуть `PR_CONFIG.ALLOW_OPERATION_WRITES=false`.

## Ограничения текущей версии

- автоматический откат из резервного листа пока не реализован;
- исполнитель обрабатывает максимум 10 подтверждённых предложений за запуск;
- применение выполняется только в DEV-книге до отдельной контрольной точки;
- merge этого блока не означает разрешение массовой очистки данных.
